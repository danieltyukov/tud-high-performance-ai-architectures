\Q{2.1 — Multiprocessing challenges}

There are two dependencies in TVB that fight each other when you try
to parallelise it:

\begin{itemize}
    \item Across timesteps, $X_j(t - d_{ij})$ has to be readable for
    every $j$ before step $t+1$ can run, so the next timestep can't
    start until the current one has finished writing its slice of
    \texttt{Xs}. There has to be a barrier per timestep. With
    $T = \texttt{tf}/\texttt{dt}$ timesteps that's a lot of barriers.
    \item Within one timestep the $N$ centres only read earlier slices
    of \texttt{Xs} and write disjoint rows, so they are independent and
    can run in parallel. That's the parallelism we can actually use.
\end{itemize}

Beyond that the practical issues are:

\begin{itemize}
    \item Communication: Python multiprocessing serialises every
    argument and every return value. \texttt{Xs} has shape $N \cdot M
    \cdot T$ doubles ($\approx 5.5$~MB for TVB192 at 60~ms, $\approx
    24$~MB for TVB998 at 15~ms) and every task needs it. Copying it
    every timestep is what kills the naive version (see Q2.2.5).
    \item Task size: one centre at one timestep is one MLP call plus
    one $N$-element sum. That's tiny compared to the cost of
    submitting a task, so you have to batch with a non-trivial
    \texttt{chunksize} (Q2.2.3).
    \item Pure-Python state: \texttt{tvb\_par.py} stores \texttt{Xs}
    as a triply-nested list. The serialiser walks every scalar
    individually instead of copying a flat block. Q2.3 fixes that with
    NumPy in shared memory.
\end{itemize}

\Q{2.2 — \texttt{tvb\_par.py} analysis}

\Qpart{1} \textit{What if the two lines were swapped (loop outside the
\texttt{with}, executor inside)?} A fresh
\texttt{ProcessPoolExecutor} would be created and shut down on every
timestep. Spinning up the pool forks all the workers, has them
re-import the module, and then tears them all down again. That's
exactly the cost the pool was supposed to avoid by living through the
whole simulation. For $T = 300$ timesteps at TVB76 the pool is built
once today; with the swap it would be built 300 times. Expected
result: a slowdown of one to two orders of magnitude. Numerical
output stays the same.

Multiprocessing is \emph{slower} than sequential at this scale. The
reason is the IPC cost. Every \texttt{executor.map} call serialises
the full nested-list \texttt{Xs} (once per task), one row of
\texttt{W}, one row of \texttt{D\_timestep}, plus a couple of
scalars. The worker decodes all of that, does $\mathcal{O}(N)$ of
pure-Python scalar work (which was already cheap), and sends the
result back. With 4 physical cores the best-case speedup is $4\times$,
but the per-message cost of moving kilobytes around dominates the
microseconds of real work, so the parallel version loses.

In the low region the curve is roughly $1/\text{chunk}$: each task

load imbalance: bigger chunks mean the last (smaller) chunk waits
longer at the barrier. The sweet spot is whatever chunk size is big
enough to amortise the dispatch cost while still keeping all 8 cores
busy.

Moving \texttt{Xs}, \texttt{W} and \texttt{D} from nested Python

orders of magnitude.

But the wall time on TVB76 and TVB192 actually goes \emph{up} a bit
relative to \texttt{tvb\_par.py} (1.84~s vs 1.48~s on TVB76, 8.54~s

now does a fresh \texttt{shared\_memory.SharedMemory(name=...)}
attach plus three \texttt{np.ndarray} view constructions, and the
hot inner loops are doing NumPy element indexing (\texttt{Xs[i, 0,
t-1]}) rather than nested-list indexing, which is slower per access
when the per-call work is small. So at small $N$ we trade one
overhead for a different overhead.

At TVB998 the per-task overhead is small relative to the
$\mathcal{O}(N^2)$ coupling sum and the absolute number lands at
69.3~s. The fix for the per-task SHM attach lives in Q2.4
(\texttt{initializer}) and the fix for the slow per-element
indexing is the vectorised kernel in Q2.6.

does by vectorising.

\Q{2.5 — When does multiprocessing pay off?}

Mostly when the per-task work is big enough that the IPC cost is
small in comparison. From the numbers above, that means:

\begin{itemize}
    \item The task body has to be heavy. Pure-Python list-indexing
    arithmetic per centre per timestep is too small. Vectorised NumPy
    is heavy enough.
    \item There has to be enough independent work between barriers.
    TVB has one barrier per timestep, but within a timestep all $N$
    centres are independent, so larger $N$ helps.
    \item Shared state has to be either small enough to pickle every
    time (rarely the case) or live in shared memory. Otherwise the
    pickle cost wipes out the parallel speedup, see Q2.2.5.
    \item The work is CPU-bound. For I/O-bound work threads are
    usually fine because the GIL is released during I/O.
    \item There are enough cores. The 8-vCPU VM has 4 physical cores,
    so the realistic ceiling is roughly $4\times$ plus a bit of extra
    from SMT.
\end{itemize}

For TVB on this hardware the takeaway is that multiprocessing only
actually wins once the inner kernels are vectorised (so the per-task
work is big enough) and state lives in shared memory (so the
per-task IPC is small). That combination is exactly what L2\_Q6
implements.

\Q{2.6 — Combined: multiprocessing + sparse + vectorisation + shared memory (\texttt{L2\_Q6.py})}

\textbf{Implementation.} I started from \texttt{tvb\_par\_sm\_imp.py}
(process pool with an \texttt{initializer}-attached SHM) and added the
two Lab 1 optimisations on top:

\begin{itemize}
    \item NumPy MLP. The two pure-Python double loops in
    \texttt{f(x, y)} become two matmuls (\texttt{np.dot}) plus an
    in-place \texttt{np.maximum} for ReLU.
    \item Sparse (CSR) coupling. The driver builds
    \texttt{(W\_data, D\_data, col\_idx, row\_ptr)} once and puts the
    arrays into shared memory alongside \texttt{Xs}. The worker's
    coupling sum becomes one \texttt{np.sum(W\_row * (x\_src - 1.0))}
    over the non-zeros of the row, with a boolean \texttt{ready} mask
    so that edges whose delay hasn't been reached yet contribute
    \texttt{W * pre(0, ...)} the same way the reference loop does.
\end{itemize}

\Q{2.7 — Throughput-oriented multiprocessing (\texttt{L2\_Q7.py})}

\textbf{Implementation.} Each worker process now runs a complete TVB
simulation. The single-process simulation kernel is the same
vectorised + sparse code as L2\_Q6, just without the inner pool. I
submit 200 of these to one \texttt{ProcessPoolExecutor}, reusing the
same $W$ and $D$ for every simulation as the assignment specifies.

\textbf{Is shared memory beneficial here?} Not really. In 2.3--2.6
the same \texttt{Xs} array was being read and written by 8
cooperating workers $T$ times, so the per-task IPC cost of copying
\texttt{Xs} was the bottleneck and shared memory removed it. Here
each simulation has its own \texttt{Xs} that no other simulation ever
touches, so there is nothing to share. $W$ and $D$ are read-only and
are pickled once per task. For TVB192 they total around 0.6~MB,
which is small next to the cost of running a 300-timestep
simulation. I'd add the SHM machinery for TVB998 (about 16~MB of
$W$+$D$) but for TVB192 it would be added complexity for no
measurable speedup.

\textbf{3. Does shared-memory optimisation transfer to threads?} No.
The whole reason \texttt{multiprocessing.shared\_memory} exists is so
that separate processes can see the same physical memory pages.
Threads inside one Python process already share all the memory by
default. Wrapping a thread pool around \texttt{shared\_memory} would
just be a no-op layer of indirection. If you want threads to scale
on CPU work, the thing to fix is to drop into code that releases the
GIL (NumPy, Numba with \texttt{nogil=True}, or a C extension).

\Q{2.9 — GIL questions}

\Qpart{1. What is Python's GIL?} The Global Interpreter Lock is one
mutex inside CPython that protects the interpreter state. Only one
thread per process can run Python bytecode at a time. CPython
releases the GIL around blocking I/O calls and around long C
extension routines that explicitly drop it (NumPy, parts of SciPy,
Numba functions compiled with \texttt{nogil=True}). It is held for
ordinary Python work like arithmetic, attribute access, and list
indexing.

\Qpart{2. Threaded TVB vs sequential.} Threaded is slower than
sequential (1.01~s vs 0.77~s on TVB76, 3.19~s vs 2.56~s on TVB192).
The kernels are pure-Python arithmetic that holds the GIL on
practically every line, so threads can't run any of it in parallel.
What you do get is the extra cost of switching between threads and
acquiring the GIL, which is why the threaded version is slower than
just running it on one thread. It still beats multiprocessing
because multiprocessing isn't getting real parallelism either at this
problem size, and threads at least don't pay the per-timestep IPC
cost of shipping \texttt{Xs} between processes.

\Qpart{3. Can multithreading alone improve sequential TVB?} No. The
hot path is pure-Python bytecode and that is exactly what the GIL
serialises. Threading would only help once the hot path has been
moved into code that drops the GIL (NumPy matmul, Numba with
\texttt{nogil=True}, Cython). At that point you usually don't need
the threads anyway because one core already runs the C kernel close
to memory bandwidth.

\Qpart{4. Where does Python multithreading alone beat sequential?}
Mostly two cases: I/O-bound work, and CPU-bound work whose hot path
is in a library that drops the GIL.

\begin{itemize}
    \item I/O fan-out: HTTP requests with \texttt{requests}, database
    queries, file reads. The GIL is dropped during the underlying
    kernel \texttt{recv}/\texttt{read}, so $k$ threads can wait in
    parallel.
    \item Disk I/O on a fast SSD, for the same reason.
    \item Code that spends its time inside C/Fortran kernels that
    drop the GIL: NumPy linear algebra (BLAS), \texttt{np.matmul},
    \texttt{scipy.linalg.solve}, Numba functions with
    \texttt{nogil=True}, image libraries like Pillow and OpenCV.
    \item \texttt{hashlib}, \texttt{zlib}, OpenSSL bindings, anything
    in compression/cryptography.
\end{itemize}

If the hot path is pure-Python bytecode like the TVB worker functions
in \texttt{tvb\_par.py}, threading on its own can't help because the
GIL pins everything to one core. Multiprocessing is the only way to
get real parallelism out of that kind of code.
