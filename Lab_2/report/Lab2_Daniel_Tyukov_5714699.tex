\Q{2.1 — Multiprocessing challenges}

The TVB algorithm has a strong \emph{temporal} dependency that
frustrates multiprocessing but a clean \emph{spatial} parallelism that
enables it:

\begin{itemize}
    \item \textbf{Across timesteps (hard).} Step $t+1$ reads
    $X_j(t - d_{ij})$ for every source $j$, so the next timestep cannot
    start until the current one has finished writing its slice of
    \texttt{Xs}. The minimum delay across all edges sets a hard barrier
    against pipelining steps. Workers therefore need a barrier (or an
    \texttt{executor.map} call) per timestep — and that barrier is paid
    $T = \texttt{tf}/\texttt{dt}$ times.
    \item \textbf{Within a timestep (easy).} All $N$ centres at step
    $t$ read \emph{only} earlier slices of \texttt{Xs} and write
    disjoint rows, so they are embarrassingly parallel. This is the
    only parallelism we can actually exploit.
    \item \textbf{Communication overhead.} Python multiprocessing
    serialises every argument (and the return value) through a binary
    protocol. \texttt{Xs} grows as $N \cdot M \cdot T$ doubles
    ($\approx 5.5$~MB for TVB192, 60~ms; $\approx 24$~MB for TVB998,
    15~ms) and is needed by every task — copying it to workers each
    timestep is the dominant cost in the naïve multiprocess version
    (Q2.2.5).
    \item \textbf{Granularity.} The work in one centre at one timestep
    is small (one MLP call, one $N$-element coupling sum) — comparable
    to or smaller than the IPC overhead of submitting a task. This is
    why a non-trivial \texttt{chunksize} is essential (Q2.2.3).
    \item \textbf{Pure-Python state.} The provided
    \texttt{tvb\_par.py} represents \texttt{Xs} as a triply-nested
    Python list, so the binary serialiser visits every scalar
    individually rather than copying a flat memory block. This is
    what shared memory + NumPy fixes in Q2.3.
\end{itemize}

\Q{2.2 — \texttt{tvb\_par.py} analysis}

\Qpart{1} \textit{What if the two lines were swapped (loop outside the
\texttt{with}, executor inside)?} A new \texttt{ProcessPoolExecutor}
would be created and torn down on \emph{every} timestep. Each spin-up
forks all worker processes, has them re-import the module, and then
shuts them down again — exactly the constant overhead the pool exists
to amortise. For $T = 300$ timesteps at TVB76 the pool is currently
created once; with the swap it would be created 300 times. The
expected outcome is a slowdown of one to two orders of magnitude with
no change in numerical results.

\textbf{Multiprocessing is \emph{slower} than sequential at this
scale.} The reason is communication overhead. Each
\texttt{executor.map} submission serialises the entire $N \cdot M
\cdot T$ \texttt{Xs} nested-list (one per task in a chunk), one row
of \texttt{W}, one row of \texttt{D\_timestep}, and the scalars; the
worker deserialises them, performs $\mathcal{O}(N)$ scalar arithmetic
in pure Python (which is already cheap), and the result has to be
shipped back. With 4 physical cores the maximum theoretical speed-up
is $4{\times}$, but the per-message overhead of $\sim$kilobytes of
serialised state per task dwarfs the few microseconds of useful work,
so the parallel version loses.

The curve is approximately $1/\text{chunk}$ in the low region: each
submission carries fixed overhead (serialisation + dispatch +

overhead $k$ times. Past the optimum the curve flattens and starts
climbing again because (a) we run out of independent parallel work —
with 8 vCPUs and chunks of size $N$, the pool only ever has $\lceil
N/\text{chunk}\rceil$ chunks, so chunks larger than $N/8$ leave cores
idle — and (b) larger chunks mean larger serialised payloads and more
imbalance between the last chunk and the rest. The sweet spot is
where chunks are big enough to amortise overhead but small enough
that all 8 vCPUs stay busy.

\textbf{Discussion.} Switching the in-memory representation of

\emph{regression} versus \texttt{tvb\_par.py} (1.84~s vs 1.48~s and

slower per access for tiny per-call work. The net "open three blocks
+ slower indexing" cost outweighs the savings on small inputs. At
TVB998 the absolute runtime (69.3~s) is dominated by the genuine
$\mathcal{O}(N^2)$ coupling work, so the per-task overhead is
amortised — Q2.4 will fix the per-task open by moving it into an
initializer, and Q2.6 will fix the slow per-element indexing by
vectorising the kernels.

\Q{2.5 — When does multiprocessing pay off?}

Multiprocessing in Python pays off when:
\begin{itemize}
    \item Tasks are \emph{coarse}: per-task work $\gg$ per-task IPC
    overhead. For TVB this means large $N$ and a non-trivial
    \texttt{chunksize}.
    \item Tasks are \emph{independent}: little or no synchronisation
    inside a barrier. TVB satisfies this within a timestep but not
    across timesteps, so we eat one barrier per step.
    \item Shared state is \emph{large but read-mostly}, or sits in
    shared memory. Otherwise the serialisation cost wipes out the
    parallel speed-up (Q2.2.5).
    \item The work is \emph{CPU-bound}, not I/O-bound. (For I/O-bound
    workloads, threads are usually the right tool — Q2.9.)
    \item There are enough cores to use. On an 8-vCPU VM the
    theoretical ceiling is $\sim$4× on physical cores; SMT typically
    contributes another $\sim$1.2$\!-\!$1.5× for arithmetic-heavy code.
\end{itemize}

In the TVB context, multiprocessing wins decisively only when
\emph{both} (i) the workload per process is large enough (large $N$,
many timesteps, NumPy-vectorised inner loops) and (ii) state is in
shared memory so we are not paying the full IPC bill.

\Q{2.6 — Combined: multiprocessing + sparse + vectorisation + shared memory (\texttt{L2\_Q6.py})}

\textbf{Implementation.} \texttt{L2\_Q6.py} starts from the
\texttt{tvb\_par\_sm\_imp.py} skeleton (process pool with
\texttt{initializer}-attached shared memory) and adds the two
optimisations from Lab 1:

\begin{itemize}
    \item \textbf{NumPy MLP.} The two pure-Python double loops in
    \texttt{f(x, y)} are replaced by two \texttt{np.dot}s and an
    in-place \texttt{np.maximum} for ReLU.
    \item \textbf{Sparse (CSR) coupling.} A driver-side
    \texttt{to\_csr} converts $W$ and the integer-delay $D$ into
    \texttt{(W\_data, D\_data, col\_idx, row\_ptr)}; these arrays are
    placed in shared memory alongside \texttt{Xs}, and the worker's
    coupling sum becomes a single \texttt{np.sum(W\_row * (x\_src -
    1.0))} over the non-zeros of the row, with a \texttt{ready} mask
    preserving the original "edge not yet reached its delay"
    semantics.
\end{itemize}

\Q{2.7 — Throughput-oriented multiprocessing (\texttt{L2\_Q7.py})}

\textbf{Implementation.} Each worker process now runs an \emph{entire}
TVB simulation (the vectorised + sparse single-process kernel from
\texttt{L2\_Q6} with the inner pool removed). 200 such simulations are
submitted to a single \texttt{ProcessPoolExecutor}. The provided
$W$ and $D$ are reused for every simulation.

\textbf{Is shared memory beneficial here?} \textbf{No.} Shared memory
was useful in 2.3–2.6 because the same \texttt{Xs} array was rewritten
and re-read across 8 cooperating workers $T$ times; the per-task
overhead of copying it dominated useful work. In the throughput
configuration each simulation has its \emph{own} \texttt{Xs} that no
other simulation ever reads, so there is nothing to share. $W$ and $D$
are read-only and are sent once per worker invocation: for TVB192 they
are $\approx$~0.6~MB total, negligible compared with the cost of
running a 300-timestep simulation. Adding a shared-memory layer would
be code complexity for no measurable win.

run on the 8-vCPU VM:

is paid once per simulation instead of once per timestep. For
workloads where many independent simulations are needed (the
parameter-fitting use-case mentioned in the introduction), the
throughput-oriented strategy is the correct one.

\textbf{3. Does shared-memory optimisation transfer to threads?} No,
not in the form we used it. The whole point of
\texttt{multiprocessing.shared\_memory} is to let \emph{separate
processes} see the same physical memory pages. Threads in one Python
process already share \emph{all} memory by default — pulling
\texttt{multiprocessing.shared\_memory} into a thread pool would just
add a no-op layer of indirection. The relevant optimisation for
threads is to release the GIL during the heavy work (drop into
NumPy/Numba/C code that runs without the GIL).

\Q{2.9 — GIL questions}

\Qpart{1. What is Python's GIL?} The Global Interpreter Lock is a
single mutex inside CPython that guards the interpreter state. Only
one thread inside a single CPython process can be executing Python
bytecode at a time. The GIL is released around blocking I/O calls,
around long C extension routines that explicitly drop it (NumPy,
scikit-learn kernels, Numba's \texttt{nogil=True}), and periodically
as a safety release; it is \emph{held} for ordinary Python arithmetic,
attribute access, list indexing, etc.

\Qpart{2. Threaded TVB vs sequential — explanation.} The threaded
version is \emph{slower than sequential} (1.01~s vs 0.77~s on TVB76;
3.19~s vs 2.56~s on TVB192) but, perhaps surprisingly, \emph{faster}
than the multiprocessed one. The hot loops (\texttt{f},
\texttt{calculate\_coupling}) are pure-Python arithmetic that holds
the GIL on every line, so adding more threads adds context-switch and
GIL-acquisition overhead on top of unchanged single-thread work —
there is no parallel speed-up to offset that overhead. It still
beats multiprocessing because the multiprocess pool also has \emph{no}
real parallelism here (the work is too small to amortise IPC) and
additionally pays the IPC cost of shipping \texttt{Xs} every timestep,
whereas threads share \texttt{Xs} for free.

\Qpart{3. Can multithreading alone improve sequential TVB?} No. The
hot path is pure-Python bytecode, which is precisely what the GIL
serialises. Threading would give a real speed-up only after the hot
path has been moved into code that releases the GIL (NumPy matmul,
Numba \texttt{nogil=True}, Cython, etc.). At that point we typically
wouldn't need threads either, because the GIL-free C kernel already
saturates one core.

\Qpart{4. Where does Python multithreading alone beat sequential?}
I/O-bound and "GIL-released-by-the-library" workloads:

\begin{itemize}
    \item \textbf{Network I/O fan-out.} HTTP requests with
    \texttt{requests}, database queries, file reads — the GIL is
    released during the kernel \texttt{recv}/\texttt{read}, so $k$
    threads can wait in parallel.
    \item \textbf{Disk I/O.} Reading many files from a fast SSD
    benefits because the kernel I/O is GIL-free.
    \item \textbf{Native C/Fortran kernels.} NumPy linear algebra
    (BLAS), \texttt{numpy.matmul}, \texttt{scipy.linalg.solve},
    \texttt{numba.jit(nogil=True)}, image-processing libraries
    (Pillow, OpenCV) — all release the GIL inside the heavy work.
    \item \textbf{Compression / cryptography.} \texttt{hashlib},
    \texttt{zlib}, OpenSSL bindings release the GIL.
\end{itemize}

For pure-Python CPU-bound code such as the TVB inner loop in
\texttt{tvb\_par.py}, only multiprocessing (separate interpreters,
separate GILs) gives real parallelism — which is exactly why this lab
walks us through that path.
